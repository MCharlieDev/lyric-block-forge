# 空行轮 V3（底层顺延） · 交接文档

> **用途**：记录本轮的背景、做法、验收与边界。配合主交接文档阅读。
> **状态**：✅ 已闭合。
> **基线**：harness 444/444；core vitest 58/58；tsc 退出码 0。
> **上游/依赖**：V3 第一批（commit 81b78d9）已用 `format.blankLines`（`leading` / `beforeLine[lineId]` / `trailing`）按行 ID 锚定空行；本轮补三项底层保真缺口。

## 一、本轮范围

修复空行的三处底层丢失：元数据块内部空行、双语合并吸收行的孤儿空行、删除锚点行后的导出丢空行；不碰 UI。

## 二、核心接口与契约变更（极其重要）

- **新增接口**：无（`parseLrc` / `buildExportText` / `serializeLrc` 的签名均未变）。
- **修改接口**：无。
- **数据模型/类型变更**：无（`blankLines` 结构保持 `leading` / `beforeLine` / `trailing`）。
- **DOM 契约（供 harness 依赖）**：无（本轮不碰 UI，面板中空行仍不可见）。

行为契约变化（非签名）：

- `parseLrc`：元数据块内部空行不再丢弃，改为随下一条内容行写入 `beforeLine[lineId]`；双语合并吞噬的被动行 id 上的空行不再丢弃，顺延到合并后的存活行 id，落空归 `trailing`。
- `buildExportText`：导出前清洗 `beforeLine`，锚点行被删（不在可见行集合）时向下顺延到最近可见行，落空并入 `trailing`；`serializeLrc` 自身「锚点不存在即丢弃」的降级契约保持不变。

## 三、关键设计与做法

- **元数据块内部空行**：`flushBlanksForMetaRow` 只在「首行之前」把 `pendingBlanks` 归入 `leading` 并清空；元数据块内部的空行留在暂存区，由后续 `placeLine` 归位到首条内容行的 `beforeLine`。文档只有元数据没有内容行时，循环结束自然归 `trailing`。
- **双语合并孤儿顺延**：先建 `presentIds`（合并后存活行 id）与 `originalIndex`（合并前行序）。按 `beforeLineBlanks` 插入顺序（即源顺序）遍历：存活锚点原位保留并追加；孤儿锚点优先挂到「时间戳集合一致」的相邻存活行（覆盖主行在前 / 在后两种合并方向），否则退化为任一相邻存活行，仍无解则收集进 `orphanTrailing`，最后 `unshift` 到真实 `trailing` 之前。数组顺序全程保持源顺序。
- **导出顺延**：`buildExportText` 在 `serializeLrc` 前对 `document.format.blankLines.beforeLine` 做一次清洗：可见锚点原样保留；孤儿锚点按 `document.lines` 原始顺序向下找第一个可见行；找不到则排进 `trailing` 最前。删除由回放层的 `removedLineIds` 表达，`document.lines` 作为基线仍然完整，因此可以精确定位「下一可见行」。
- **不引入 OperationKind**：空行仍是 `format` 侧的附加数据，不进入操作日志；删除 / 插入空行不产生独立撤销记录（见「已知取舍」）。

## 五、验收证据

- **tsc**：`npx tsc -b --noEmit` 退出码 0
- **vitest**：`npx vitest run` 通过 58/58（原 55 + 新增 3）
- **harness**：`npm run harness` 444/444，0 失败（重点确认原空行/导出行相关组未回归）
- **关键断言/实测**：
  - `'[ti:a]\n\n[ar:b]\n[00:01.00]x\n'` → 空行落在首条内容行 `beforeLine`，序列化为 `'[ti:a]\n[ar:b]\n\n[00:01.00]x\n'`（空行保留，位置归一到元数据块之后）。
  - `'[00:01.00]中文\n\n[00:01.00]English\n'` → 合并为 1 行，空行挂到存活行 id，序列化为 `'\n[00:01.00]中文\n[00:01.00]English\n'`。
  - `'[00:01.00]a\n\n[00:02.00]b\n[00:03.00]c\n'` 删除 b（回放 `removedLineIds`）后 `buildExportText` 输出 `'[00:01.00]a\n\n[00:03.00]c\n'`。

## 六、已知取舍与未验证

- **取舍**：
  - 空行在面板中完全不可见，创作者在编辑界面感觉不到空行的存在，直到导出 LRC 时才体现。
  - 连续删除多行时，空行会向尾部累积（顺延策略的副作用）。
  - 未引入 `OperationKind`，删除 / 插入空行无法通过撤销记录单独回退。
  - 元数据块内部空行只能「保留数量与顺序」，无法逐字原位：`serialize.ts` 本轮未改，空行统一落到元数据块之后、首条歌词行之前。
- **未验证**：
  - 未做真机 / 浏览器人工目测（导入含元数据空行的 LRC、删行后导出、双语跨空行合并导出）。
  - harness 无 `blankLines` 断言，导出空行行为仅由 core vitest 覆盖。

## 七、否决的备选方案

- **改 `serialize.ts` 在元数据组之间插入空行**：能实现逐字原位，但会引入第 4 个文件、越过本轮硬边界，且需要扩展 `blankLines` 数据结构；本轮按任务书 fallback 归一到首条内容行之前。
- **在 `parse.ts` 内直接过滤被删锚点（提前顺延）**：删除发生在回放层，解析期看不到 `removedLineIds`；若在解析期猜位置会与基线文档脱节，因此把删除场景的顺延放到 `buildExportText` 的导出清洗阶段。
