## 一、本轮范围

把元数据前缀识别器的硬编码前缀表提取为可导出的默认表，并允许调用方通过 `ParseOptions.metadataPrefix.rules` 整表替换；同时给每条规则增加 `action: 'meta' | 'line'`，支持「命中后保留为歌词行、绝不转元数据」。本轮只做内核，不接 UI、不碰序列化。

## 二、核心接口与契约变更（极其重要）

- **新增接口**：
  - `MetadataPrefixRule`：`{ prefix: string; tag: string; action?: 'meta' | 'line' }`。用途：描述一条前缀规则，`tag` 为写入 `applyMetaTag` 的标签名；`action` 缺省 `'meta'`。
  - `DEFAULT_METADATA_PREFIX_RULES: MetadataPrefixRule[]`：原硬编码 9 条默认前缀，`action` 全缺省。
  - `matchMetadataPrefix(line: string, rules: readonly MetadataPrefixRule[])`：返回 `{ tag, value, action } | null`，首个命中即返回。
- **修改接口**：
  - `ParseOptions.metadataPrefix`：原 `{ enabled?: boolean; keepLyricLine?: boolean }` → 现新增 `rules?: MetadataPrefixRule[]`。
  - `matchMetadataPrefix`：原签名为 `(line: string)` 且读模块内硬编码表 → 现签名为 `(line, rules)`，由调用方决定规则表。
- **数据模型/类型变更**：
  - `MetadataPrefixRule`：新增 `action?` 字段（`'meta' | 'line'`）。
- **DOM 契约（供 harness 依赖）**：
  - 无。本轮为纯 core 内核，不改 DOM、不改 `data-*`、不改 class。

## 三、关键设计与做法

1. **整表替换语义**：主循环用 `options.metadataPrefix?.rules ?? DEFAULT_METADATA_PREFIX_RULES` 取表。用 `??` 而非 `||`，保证显式传入空数组时不会回退默认表（空数组 = 全部不识别）。
2. **非法规则静默跳过**：新增 `isValidMetadataPrefixRule`，空 `prefix`、空 `tag`、`prefix` 含 `：: \t` 任一分隔符即判非法；循环内 `continue`，不抛错、不阻断后续规则。
3. **重复 prefix 先到先得**：`matchMetadataPrefix` 顺序遍历规则，命中第一条合法规则立即 `return`，后续同前缀规则不再参与。
4. **action 分流**：命中结果带 `action`；主循环只在 `matched.action === 'meta'` 时走原有「写 `metadataTags` + `applyMetaTag` + 可选 `keepLyricLine` 保留行」逻辑。`action === 'line'` 与未命中一样自然落到 `placeLine`，因此：
   - 绝不写元数据；
   - 不注入 `00:00.000`；
   - 全局 `keepLyricLine` 对它无效（保留为歌词行是最高优先级）。
5. **沿用既有触发窗口**：规则仍只在 `recognizeMetadataPrefix && withinPrefixWindow && !sawTimestamp` 时匹配，即前 10 条内容行、首条带时间戳行之前、总闸门与 `enabled` 均开启；窗口逻辑本轮未改。
6. **`rule.tag` 直传 `applyMetaTag`**：标准标签名进对应字段，非标准标签名继续走既有 default 分支 → `meta.custom[tag]` + `unknownTags`，前缀路径与 `[tag:value]` 路径共用同一份映射。

## 六、已知取舍与未验证

- **取舍**：
  - 规则一旦传入就完全替换默认表，调用方需自行合并默认表（为后续 UI 提供完全控制权）。
  - `action: 'line'` 的规则会跳过所有元数据合并，全局 `keepLyricLine` 对它无效。
  - 本轮未实现通过正则或模糊匹配前缀，只支持精确前缀匹配。
  - 本轮未将冲突（如同前缀多值）录入建议层。
  - 识别成功仍是有损转换：原文不回写，导出为 ASCII 标签名（沿用内核轮裁决）。
- **未验证**：
  - UI 可达性：本轮未接 SettingsMenu / settingsStore，界面无自定义规则入口（预期）。
  - 真机 / 人工目测：纯内核，未做人工目测。
  - 冲突建议层：同前缀多值、误识别的人工纠正路径未实现。

## 七、否决的备选方案

- **把 `rules` 与默认表合并（增量语义）**：调用方只写差异、默认表兜底。否决原因：用户/决策 AI 明确要求「传入即完全替换」，合并会让「删除默认前缀」无法表达；后续 UI 需要完全控制权。
- **在 `matchMetadataPrefix` 内按 `action` 直接返回不同结构，或给 `action:'line'` 单独写一条保留分支**：否决原因：会让「保留为歌词行」重复 `placeLine` 逻辑，且容易误带 `keepLyricLine`；当前「不命中 meta 分支即自然落 `placeLine`」更少代码、语义更硬。
- **对非法规则抛错或整体拒绝解析**：否决原因：规则来自未来用户配置，单条脏数据不应让整次导入失败；静默跳过 + 首条合法命中优先更稳。
