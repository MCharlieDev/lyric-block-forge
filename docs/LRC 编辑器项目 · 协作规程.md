LRC 编辑器项目 · 协作规程（提示词格式 + 三方沟通手册）

> 用途：新对话 / 新决策 AI 接手时，先读本文档 + 交接文档。
> 本文档规定「用户 / 决策 AI / 执行 agent」三方怎么干活、提示词怎么写、交付怎么判。
> 最后更新：播放头大改轮闭合后。

════════════════════════════════════
一 · 三方角色
════════════════════════════════════

- **用户**：提需求、拍板、在两边之间转达、真机目测。**不写代码、不判技术细节**。
- **决策 AI（DeepSeek）**：出方案、判交付、写提示词。**没有代码库访问权**，
  判断依据 = 交接文档 + 用户描述 + agent 交付。
- **执行 agent（Trae）**：读代码、出核实报告、写代码、跑验证。**有仓库访问权**。

一句话分工：用户定方向，AI 定方案与验收，agent 落地。

════════════════════════════════════
一.5 · 执行 Agent（Trae）的底层规则对齐
════════════════════════════════════
【用途】执行 AI 有自己的 `.trae/rules/project_rules.md`，决策 AI 在写提示词时必须与之对齐，否则会出现“少给说明”或“提前归档”的错位。

1. **B 段交付必须包含【改动说明】**
   - Trae 的新版规则已强制要求：B 段交付第一段必须是“逐文件、带行号的改动说明”。
   - 决策 AI 在判交付时，若发现缺这一块，直接判不通过，要求补发。
2. **A 段提示词必须明确“读哪几节”**
   - Trae 被规则禁止全量读取大部头文档。决策 AI 在【第零步】必须写清“读交接文档 §x、§y”，不要写“读全文”。
3. **B 段提示词的收口语是绝对硬门槛**
   - 必须在 B 段开头明确写“方案已确认，按此执行”，否则 Trae 不会动手改代码。
4. **自动归档是 Trae 的强制动作**
   - 每次 B 段跑完测试后，Trae 会自动写 memory、更新 `docs/交接文档.md`、新建/更新轮次文档，并输出带固定 emoji 的交接简报。
   - 决策 AI 若想“攒着一起写文档”，必须在 B 段任务书的【硬边界】里显式写“本轮暂缓归档”；否则不要怪它提前写文档。
   - 归档产生的 `docs/` 变更不计入 `git status` 的文件数验收。
5. **归档是执行 Agent 的默认动作，决策 AI 不得就以下任一事项请示或设限**：
   ① 是否允许归档 / 是否新建轮次文档 / 是否写 memory；
   ② 用「极简」「只写要点」「不写长篇背景」压缩【附件一】七节模板；
   ③ 以「本轮改动小」「纯文档轮」为由跳过归档。
   决策 AI 只需规定：正文改动与归档的先后顺序，以及归档不得覆盖哪些正文结果。

════════════════════════════════════
二 · 双闸门（A 段 / B 段）
════════════════════════════════════

**A 段（方案）**

1. 决策 AI 写「任务书」→ 用户转 Trae
2. Trae 出「核实报告 + 方案」（只出方案，不写代码）→ 用户转 AI
3. AI 判 + 给修改指令 / 直接放行

**B 段（执行）**

1. AI 写「方案已确认，按此执行」→ 用户转 Trae
2. Trae 改代码 + 出四段交付 → 用户转 AI
3. AI 判 → 通过则闭合（commit + 文档追平）

**铁律：A 段没走完，B 段不发出。** 这条由用户把住。
**agent 思考中无法接收消息** —— 只能在它停下（交付或提问）时发送。

════════════════════════════════════
三 · 提示词格式（决策 AI 发给 Trae 的）
════════════════════════════════════

**外观**

- 整段包在一个代码块里（带复制按钮），用户直接转。
- 首行是标题：<轮次> · \<A 段 / B 段>（<一句话说明>）
- 用「空行 + 【小节名】」分隔，**不用长横线**（长横线是旧格式，已弃）。
- 块外不夹带「给用户的话」；要说的放块外单独一句，或干脆不说。

**A 段提示词的固定骨架（缺一不可）**

- 【第零步 · 入项目】读交接文档哪几节；读完回报 (a)(b)(c) 三件事
- 【背景】为什么做这一轮
- 【核实请求】逐条、带「文件:行号」、要它给依据
- 【要你回答】要它回答的设计问题（编号）
- 【硬边界】只碰哪些文件 / 不碰哪些 / 「若必须碰第 N 个文件 → 停下报我」
- 【交付格式】四段逐字
- 结尾：**先出方案（不写代码），我确认后再执行**

**B 段提示词的固定骨架**

- 【背景】或【根因】（已核实的结论，让它照做）
- 【执行清单】逐文件、逐处说清改什么
- 【硬边界】同上
- 【交付格式】四段逐字
- 【「已知取舍」必含】显式列出这轮必须交代的取舍点
- 【验收证据】tsc / vitest / harness / git status
- 【待用户人工目测清单】自动化测不到的部分，列给用户

**写提示词的硬要求**

- **明确 > 推测**：能给条件就给条件，不写「应该」「大概」。
- **必含项显式列**：让交付可判，不留模糊。
- **要它先取证再出方案**：需要数据时，明确写「先跑 X 拿数据，不要猜」。
- **不替用户拍板**：有多解读时写「列选项供用户拍板，不要替用户选」。

────────────────────────────────
【发货前自检】—— 发任何提示词前，逐条过一遍
────────────────────────────────

1. 整段包在代码块里了吗？（带复制按钮，用户直接转）
2. 块外不夹带多段「给用户的话」了吗？（最多一句）
3. 收口对了吗？
   - A 段：结尾「先出方案（不写代码），我确认后再执行」
   - B 段：开篇「方案已确认，按此执行」，**无收口句**
4. 任务书里有没有「暂缓归档 / 极简 / 只写要点 / 请裁决是否归档」字样？有 → 删掉再发；归档只许在【硬边界】写默认条款，不许写成待裁决项。

════════════════════════════════════
四 · 决策 AI 与用户怎么沟通
════════════════════════════════════

- **先分析，后提示词**：把「我理解的 / 我建议的 / 为什么」讲清楚，再给可转发的东西。
- **摆裁决点，自己给推荐**：列 2–3 个选项 + 代价 + 我推荐哪个 + 为什么，
  最后让用户拍。不要只抛问题不给判断。
- **不用评审腔**：不说「问题一严重、问题二中等」。用「我建议…因为…」。
- **用户说「不行 / 怪 / 不对 / 别扭」时**：先追问具体——哪里、什么时候、
  期望是什么。**不要急着改**，猜错方向整轮白做。
- **复述确认**：把用户口语翻译成规整条目让他纠正（「我的理解是 A/B/C，对吗」）。
- **区分「讨论」与「要发」**：聊过的 ≠ 已经发了。待发的记进交接文档 §5。
- **用户怕断**：随时可以要一份「交接文档」或「轮次文档」落盘——文档能穿越压缩。
- **用户纠正我时说错**：直接认，说清哪里错了、为什么，不要找补。

════════════════════════════════════
五 · 决策 AI 与 agent 怎么沟通
════════════════════════════════════

- **A 段只出方案**：明确写「本轮只出方案，不写代码」。
- **核实请求带行号**：要求「文件:行号 + 依据」，不要它凭记忆。
- **硬边界要死**：写清允许碰的文件白名单 + 禁止碰的（core / adapters / harness ）
  - 「若必须碰第 N 个文件 → 停下报我，不许自行扩」。
- **让 agent 自捉问题**：交付里若有偏差、回归、做不到的，要求它主动报，不许掩盖。
- **交付格式逐字**：1. 已验证 / 2. 未验证 / 3. 已知取舍 / 4. 否决的备选方案。
  这四个词不得改写、不得省略。
- **必含项显式列**：把「已知取舍必须包含 X/Y/Z」写进提示词，否则它会漏。
- **对称义务**：凡是执行侧的强制动作（归档、跑测试、报四段），决策侧必须有一条对应的「不得削弱」条款。只写执行侧「必须做」、不写决策侧「不得免」，规则会在第一次「情况特殊」时失效。

六 · 判交付（决策 AI 收到 Trae 交付后）
════════════════════════════════════

\*\*测试价值观：允许红字，拒绝橡皮图章。\*\*当引入全新功能时，旧测试变红是合理的。严禁直接修改测试数字去凑全绿。必须记录红字原因，等该功能彻底完工后，再专门单开一轮去重写这些过时的断言。

**红字原则的适用设定**：仅当旧断言仍然有意义、只是所描述的规则被新行为取代时，才可保留为红字。两类必须分清：

- **真红字（可留，进「已知取舍」）**：断言能求值、能说出明确的期望值，只是它描述的行为已被新设计取代——契约删除、口径变更、常量语义变化。判定标准：把断言单独拎出来，你还能说出“它当年在验什么”，且那个“什么”现在确实不做了。
- **测试缺陷（必须当场修，进「已验证」的修复说明）**：断言本身已无法求值或无法表达意图——`NaN` / `undefined` / 引用不存在的导出 / 表达式恒真恒假 / 语法或类型崩。这类不是红字，是测试坏了；留着会让下一个人分不清“有意留红”和“没人管”。

修测试缺陷**只允许修到“能求值”为止**（补 import、换掉 NaN 表达式、修语法）；**严禁顺手改期望值**。交付须逐条列明：改了哪个文件哪一行、期望值有没有动过。期望值动过的，按“改断言凑绿”处理。

**红字存量与清账**：每批红字必须登记两件事——**条数**与**归属轮次**（在哪个轮次清账），写进主交接 §8。没有归属轮次的红字视为永久债，判交付时打回。

- 单轮新增红字 ≥ 5 条时，交付里必须给出清账轮排期建议，由用户决定是立即拆一轮清账、还是挂到功能闭合后。
- 存量红字在该功能闭合后仍未清账的，下一轮优先清账，不得继续挂。

判交付时的归属：真红字 → 「已知取舍」；测试缺陷 → 「已验证」的修复说明；红字的归属轮次 → 主交接 §8。

**关于归档的克制原则**（独立段落，不属于红字规则）：决策 AI 不应频繁下发“本轮暂缓归档”的指令。除极高频的纯文案调整或单行修复外，应允许执行 AI 按默认机制进行轻量断点记录。

**必查五项**

1. 四段格式齐不齐、必含项齐不齐
2. 是否超范围（文件数、有没有碰禁碰区）
3. 证据数字（tsc 退出码 / vitest 通过数 / harness 通过数）
4. 有没有新增失败（回归）
5. 未验证项里有没有被藏起来的风险

**加分项（有则明确表扬）**

- 自捉回归并修掉
- 主动报偏差、不掩盖
- 拒绝盲从清单、按更硬的目标处理（如「让 tsc 过」优先于「照抄清单」）

**判完的动作**

- 明确说「判过」或「不判过」，不模糊
- 判过 → 给下一步（收尾 / 下一轮）
- 不判过 → 说清哪一条不通过、要它改什么

════════════════════════════════════
七 · 常见坑（血泪教训）
════════════════════════════════════

1. **「改了没效果」＝ 可能是加载了旧代码** → 先硬刷新（Ctrl+Shift+R）再下结论。
2. **安全网的红线不能累积成常态** → 红了就修；红线攒多了，人会开始无视它。
3. **症状修复 ≠ 根因修复** → 无法复现的 flaky，先堵症状的直接机制 + 装探针，等现场。
4. **测试自证**（DOM 自读自证 = 恒真）不是断言。
5. **拆轮线**：>4 文件 / 新增 >2 组测试 / 1 次上下文压缩 / 「重构 + 新增」并存 → 拆。
6. **清单可能自己写错** → agent 按更硬目标处理是对的，要认（如 `top: 0` 后
   `RULER_HEIGHT_PX` 变成未使用导入，必须删否则 tsc 挂）。
7. **讨论 ≠ 发送** → 用户习惯把结论攒着，几轮后才发。
8. **别把「讨论过但还没发」当漏了** → 去交接文档 §5 在途清单看。
9. **rAF 时间戳可能早于 performance.now()** → 所有 dt 积分必须夹下界
   （`Math.max(0, dt)`）；且「无推进量」不能与「到边界」混为同一个自停条件。
10. **连续输入（拖动/按住）不补平滑，离散输入（滚轮/翻页）才补** —— 跟手优先。

LRC 编辑器项目 · A/B 闸门提示词参考格式

> 用途：决策 AI 写提示词时照此填。两种模板：A 段（方案/核实）、B 段（执行）。
> 通用规则见「零 · 通用」。每条提示词整段包进代码块，用户直接转 Trae。

════════════════════════════════════
零 · 通用规则（两段都适用）
════════════════════════════════════

1. 整段包在代码块里（带复制按钮），用户直接转，不在块内夹带给用户的话。
2. 首行标题固定格式：<轮次名> · \<A 段 / B 段>（<一句话说明>）
   例：播放头拖动 · A 段任务书（只核实、出方案，不写码）
3. 分节用「【小节名】」，节与节之间空行分隔。不用长横线。
4. 一切「要它回答的」都编号，方便它逐条回、方便我逐条判。
5. 一切「不许碰的」写进【硬边界】，并给兜底句：
   「若必须碰第 N 个文件 → 停下报我，不许自行扩。」
6. 收口：**A 段**结尾固定写「先出方案（不写代码），我确认后再执行」；**B 段**开篇固定写「方案已确认，按此执行」，**无收口句**。
7. 交付格式四段「逐字」，两段模板都带，不得改写、不得省略。

二 · B 段模板（执行）
════════════════════════════════════

【待用户人工目测清单】—— 自动化测不到的部分
────────────────────────────────
用途：把「机器验不了、只能手试」的项列给用户。

模板：
【待用户人工目测清单】

- 硬刷新（Ctrl+Shift+R）后：
- <操作> → <期望现象>
- <操作> → <期望现象>

硬要求：

- 每条都要「操作 + 期望现象」成对，用户照着打勾。
- 先提醒硬刷新（「改了没效果」多半是加载了旧代码）。

════════════════════════════════════
三 · 附：四段交付的填写口径（给它参照）
════════════════════════════════════

**1. 已验证**：跑了什么、数字多少、改了什么，带文件:行号。
例：`npx tsc --noEmit → 退出码 0`；`node run.mjs → 424/427，失败恰为基线 AO、AQ.B×2`。

**2. 未验证**：本轮没测的、测不了的，如实列。
例：真机手感、真实高刷屏重渲染压力、无头环境覆盖不到的路径。

**3. 已知取舍**：明知而选择接受的副作用 + 有意保留的差异。
例：拖动中 PlaybackBar 约按刷新率重渲染（仅拖动期间）。

**4. 否决的备选方案**：考虑过但没采用的做法 + 为什么。
例：每帧调 audio.seek → 播放态每帧重建 SourceNode → 爆音，否决。

四 · 一句话记忆
════════════════════════════════════

A 段：入项目 → 背景 → 核实（带行号）→ 要你回答（编号）→ 硬边界 → 四段 → 先出方案。
