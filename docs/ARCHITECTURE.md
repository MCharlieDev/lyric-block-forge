# LRC 歌词编辑器 —— 完整架构设计提示词

以下内容是我们从开头到现在的全部讨论成果。**用户原话部分未做任何修改，直接引用。** 请将此作为开发参考，严格遵循已敲定的设计。

---

## 一、项目定位与目标

- 制作一个 LRC 歌词文件编辑器。
- 核心定位：**辅助创作者**，不是傻瓜编辑器。给创作者最大的方便和权限。
- 用户原话：
  > “频率微调当然是需要用户点按钮才能识别微调我们做的这个不是一个傻瓜歌词编辑器。是要尽可能的方便创作者去实现的，就是给创作者最大的方便以及权限。”
  > “以辅助创作者的角度思考。每一个重大改变都是需要弹窗提示。撤销的记录保留可见可以回复”

---

## 二、平台与打包

- 需要覆盖：Web、Windows exe、Android、iOS。
- 用户原话：
  > “Web可打包为exe程序，然后还要可以提供一个程序，能在手机平台上运行使用。”
  > “Q1的话尽量都兼容。Q2尚不考虑上架应用商城，主要为内部分享Q3手机端的功能要和电脑端大致相同Q4应用设计为离线程序不需要做同步Q5不主动限制文件大小，需要波形，方便查看Q6行级字级都要，这个应该没那么多区分吧？功能实现应该大差不差Q7问题不理解，我基础没那么好如果想让我回答，建议再描述清楚一点向我详细介绍一下”
- 技术路线敲定：
  - 核心逻辑一份（纯 TypeScript），UI 尽量共享，平台能力用适配层隔离。
  - 桌面 exe：Tauri 2 或 Electron（推荐 Tauri 2）。
  - 移动端：Capacitor 打包 Android/iOS。
  - Web：PWA，直接部署。
  - 不追求“纯一套代码”，追求“核心一套、UI 共享、平台隔离”。
- 用户原话：
  > “我觉得编同一套代码，然后能分别打包不同的更好，但是主要重心应放在实现全部功能，而不是嗯，方便转移架构，这个你再仔细考虑一下。”

## 三、总体架构分层

- **表现层**：共享 UI 组件，桌面/Web 布局，移动布局。
- **应用层**：用例编排、命令总线、查询服务、会话管理。
- **领域层**：歌词文档模型、时间轴、同步引擎、操作日志、建议层、校验层、音频分析。
- **平台适配层**：FilePort、AudioPort、StoragePort、ClipboardPort、SharePort、NotificationPort、HapticsPort、ShortcutPort、WaveformCachePort、AudioAnalysisPort。
- **外壳层**：Web 壳、Tauri 桌面壳、Capacitor Android/iOS 壳。
- **原则**：文档状态、播放状态、编辑器状态分离；所有修改走命令；解析/序列化尽量无损。

---

## 四、核心领域模型

- **LyricDocument**：元数据、行集合、音频引用、格式信息、脏标记、版本、恢复信息。
- **LyricLine**：行 ID、主文本、翻译、罗马音、注释、行时间戳、字级时间戳集合、角色、状态。
- **Timestamp**：类型（行级/字级/区间）、时间值（内部统一毫秒整数）、精度、关联文本范围、来源。
- **AudioAsset**：音频源、时长、波形缓存、节拍/静音检测结果（扩展）。
- **Selection**：行选择、字选择、时间范围选择、多选与跨行选择。
- **操作日志记录**：操作 ID、类型、时间、影响范围、变化量、描述、状态。
- **建议模型**：建议 ID、类型、影响范围、建议值、置信度、状态。
- **校验模型**：问题 ID、类型、影响范围、严重程度、建议修复方式。

## 五、分级回退与操作日志

### 5.1 最终模型：带类型的操作日志

- 每一次修改时间戳，都往一个全局日志里追加一条记录。
- 每条记录带：类型（手动打轴/整体移动/多选移动/频率微调/手动微调等）、范围、变化量（绝对值或偏移量）。
- 当前时间戳值 = 从头回放所有未被撤销的操作后得到的结果。
- 普通撤销：弹出最后一条，重放剩余操作。
- 按类型撤销：删除所有该类型的记录，重放剩余操作。
- 支持筛选、多选、批量撤销、恢复。
- 用户原话：
  > “对于回退那部分也可以加一个多选加一个筛选这样子可以筛选修改类型，然后多选或全选想要修改的部分”
- 性能：操作数量通常几百到几千条，回放毫秒级，无需担心。极端情况可加快照。

### 5.2 重大改变弹窗提示

- 整体偏移、多选偏移、批量撤销、频率微调批量应用，必须弹窗。
- 弹窗写清：影响哪些行、变化量、撤销后能否恢复。
- 单行手动打轴、单行手动微调不弹窗，直接进日志。
- 用户原话：
  > “每一个重大改变都是需要弹窗提示。撤销的记录保留可见可以回复”

### 5.3 撤销记录保留可见、可恢复

- 已撤销的记录灰显，不删除。
- 可勾选已撤销记录，点“恢复所选”，重新生效。
- 恢复同样走日志重放机制。
- 筛选里可选“只看生效”“只看已撤销”“全部”。

## 六、波形与时间轴

### 6.1 三层拆分

- **波形层**：只画音频波形，不认歌词，只认时间。
- **时间轴层**：时间刻度、缩放、滚动、播放头、选区。
- **歌词块层**：画歌词块、拖动、选中、吸附。
- 共享时间坐标系：内部毫秒整数，像素映射 `x = (time - viewStart) * pixelsPerMs`。

### 6.2 波形本体不可侵犯

- 用户原话：
  > “你弄的这个像是把创作者当傻子。创作者既然是要打洲的，就肯定是能分辨出波形的样貌你标的这么明显，是生怕创作者看不见。我建议是增加一个小标记去提供建议。而不影响创作者对波形图的主观感受”
- 设计原则：不遮挡波形本体、不改变波形颜色、不覆盖波形区域、可一键关闭、建议和确认要区分。
- 人声/间奏标记放在波形上方或下方的独立“分析轨”，窄条，只画边界线或小三角。
- 预备提示：播放头前方的小标记，接近人声区起点时轻微闪烁或变大，不改变波形颜色。手机可加轻微震动。
- 建议边界用虚线或半透明，用户确认后的边界用实线，手动修正的用另一种样式。

### 6.3 歌词块拖动

- 用户原话：
  > “使用歌词块的方法是因为我之前，大多数编辑器只能通过输入时间戳的方式进行修改。但是如果能够拖动歌词块，就能比较直观的去修改。”
- 拖动行级：字级时间戳整体平移，保持相对间距。
- 拖动字级：只改该字起始时间，行级不变，非法位置阻止并提示。
- 拖动多选：所有选中行一起移动，相对间距不变。
- 拖动过程中不写日志，松手时才生成一条操作记录。
- 吸附：吸附到播放头、其他行时间戳、网格线、节拍点、人声起点。吸附阈值用像素算，显示对齐辅助线。

## 七、字级跟随行级

- 主流播放器遇到冲突不会“报错”，而是“显示异常”。因此编辑器应主动避免冲突。
- 用户原话：
  > “针对你这个问题的行集和字集，他们在那些音乐软件中实施的时候，如果有冲突，会发生什么报错呢？如果会发生一些实质性的报错的话，那就按照跟随的方式去改，不需要添加其他方式了，毕竟那些已经是报错的东西”
- 最终策略：
  - 拖动行级 → 字级整体平移（唯一策略，不提供其他模式）。
  - 拖动字级 → 只动那个字，非法位置阻止。
  - 不提供“只改行级”“按比例缩放”等选项。
  - 冲突由校验层处理，不靠用户手动选模式。

## 八、导入与识别规则

### 8.1 核心原则：预设前置，异常兜底

- 用户原话：
  > “在导入文件的时候，应该把预先设置作为重点，把事后确认作为替补。毕竟导入文件这一件事情应该简单化，而不是让创作者去重复确认它”
- 导入主流程：输入源 → 格式检测 → 解析 → 规范化 → 按预设识别 → 直接写入文档 → 仅异常进确认。
- 用户配置一次，之后每次导入按配置走，不弹逐条确认。
- 事后确认只处理：编码检测失败、格式无法识别、预设冲突、严重冲突、未知标签（原样保留，导出写回，不弹确认）。

### 8.2 预设内容

- 元数据前缀规则（作词、作曲、演唱等，可增删，识别后转元数据或保留歌词行）。
- 双语识别规则（分隔符、主语言、合并方式）。
- 时间戳规则（支持格式、精度）。
- 编码规则（默认编码、备选）。
- 冲突处理规则。
- 识别器开关与顺序。
- 预设只是简单设置，不需要导入导出。用户原话：
  > “预设只是一些简单的设置，不需要专门导入导出”

### 8.3 识别器

- 元数据前缀识别器：识别歌词前介绍，中文冒号、英文冒号、空格、制表符等。
- 双语识别器：支持换行、斜杠、竖线、自定义符号。用户原话：
  > “双语识别分隔符可以识别换行之类的，可以像你说的那样，让用户自定义一个这一个没什么好讨论的”
- 时间戳识别器：识别非标准 LRC 格式的时间戳。
- 结构识别器：段落、空行、注释。
- 所有识别结果进建议层，高置信度一键接受，低置信度逐条确认。用户可拒绝、修改后接受、忽略全部。
- 识别规则可配置：前缀列表、分隔符、时间戳格式、开关、顺序。配置持久化到偏好设置。

### 8.4 Word 导入

- 用户原话：
  > “word导入当然是纯文本，它只是一个歌词，不需要什么复杂的格式”
- 只提取纯文本，不保留格式、样式、图片。

## 九、日志面板

### 9.1 定位：工作日志

- 用户原话：
  > “就像创造一份工作日志一样。每一次的工作都是不一样的嘛，单独建立工作日志就行了。用分页签以及有一个总的页签分页前按时间顺序显示修改或报错的内容。总页签就将修改与报错全部按时间顺序排列。按操作顺序排列”
- 每个文档一份独立日志，随文档保存，不跨文档共享。
- 打开文档即可看到从创建到现在的完整工作历史。

### 9.2 五个页签

- **总**：所有记录按操作顺序排列，已归档和已忽略折叠显示。
- **修改**：只看修改记录，含生效和已撤销。
- **报错**：只看报错记录，含待处理、已修复、已忽略。
- **已归档**：装“撤销”和“已处理”两类。
- **忽略**：装被忽略的报错。
- 用户原话：
  > “再加一个已处理和忽略的分页签这里面显示那些已经处理和被忽略的项。而在总页签里面已经处理和被忽略的显示为折叠状态。”
  > “已处理这个分页的名字起的不太好。我想放在这里面的内容应该是那些去掉的不要的操作。和对报错处理过的操作。这些都是不需要在总页里面时时看见的东西”
  > “名字需要更精确一点，比如撤销的动作类型描述叫撤销，但归档在已归档的这个分页名里头然后处理的报错叫已处理但也归档在已归档这个分页的名目里头”

### 9.3 总页签的折叠方式

- 用户原话：
  > “折叠的话，其实折叠的那些也显示在操作顺序里面只不过只显示成一条很细的，然后介绍也很简单的一条不像其他的那些操作日志显示详细信息。是这么一个折叠方式。也可以在设置里面调整，完全不显示在总页里面只可以在已归档和已忽略里面查看”
- 已归档和已忽略的记录仍在时间顺序里占位，只显示为一条细行。
- 细行只显示：时间 + 动作类型 + 大类（如“撤销 整体移动”“已处理 时间倒置”），不显示毫秒数、行号、具体数值。
- 点击细行跳转到“已归档”或“忽略”页签，查看完整详情。
- 不跳转到时间轴，因为撤销/已处理的操作效果已从时间轴移除，没有对应位置。
- 设置里三种显示模式：细行（默认）、完全隐藏、正常显示。

### 9.4 已归档页签

- 装“撤销”和“已处理”。
- 排列方式：混排按时间 / 分两组，设置里切换。用户原话：
  > “Q2，2种形式都可以保存要修改的话就去设置里面”
- 撤销类显示：原操作类型、影响范围、原变化量、撤销时间，可恢复。
- 已处理类显示：报错类型、影响范围、修复方式、修复时间，可取消处理。
- 点击细行跳转到已归档页签，查看具体内容。用户原话：
  > “Q3就是去查看修改了什么东西的具体内容，方便创作者查看”

### 9.5 忽略页签

- 只装被忽略的报错，可取消忽略，回到待处理。

### 9.6 状态与页签对应

| 记录类型 | 状态 | 出现在 |
|---|---|---|
| 修改 | 生效 | 总、修改 |
| 修改 | 已撤销 | 总（细行/隐藏/正常）、已归档 |
| 报错 | 待处理 | 总、报错 |
| 报错 | 已修复 | 总（细行/隐藏/正常）、已归档 |
| 报错 | 已忽略 | 总（细行/隐藏/正常）、忽略 |

## 十、音频分析策略

### 10.1 目标

- 只服务两件事：**频率微调**、**人声边界识别**。
- 一套分析管道，两种输出。
- 用户手动触发，不自动跑。

### 10.2 四层管道

1. **预处理**：解码 PCM，分帧（20-50ms，重叠），加窗。
2. **特征提取**：短时能量、过零率、频谱质心、频谱滚降、基频、MFCC。推荐使用 Meyda.js。
3. **判定**：双门限比较法（推荐起步）、多特征融合、集成 VAD 库（进阶）。
4. **应用输出**：
   - 频率微调：给定粗略时间戳，返回建议精确时间戳。
   - 人声边界：返回人声区间列表。

### 10.3 触发与缓存

- 频率微调：用户点按钮，只分析选中行附近（前后 500ms）。
- 人声边界：用户点按钮，分析整首歌，显示进度条或后台跑完通知。
- 缓存：预处理和特征提取结果分块缓存，与音频文件指纹绑定。人声边界结果缓存。桌面写文件，Web/手机写 IndexedDB 或原生存储。

### 10.4 精度与修正

- 频率微调：毫秒级，帧长要短，重叠大，可用抛物线插值。
- 人声边界：百毫秒级，帧长可长，减少计算量。
- 用户可修正人声边界：拖动边界线、新增、删除、合并、拆分。修正动作进日志。
- 建议进建议层，用户确认后才写入文档。

### 10.5 跨平台实现

- 核心层定义 AudioAnalysisPort 接口。
- Web：Web Worker + Web Audio API 或 WASM。
- 桌面：Tauri 可用 Rust 做分析。
- 手机：Capacitor 原生插件或 WASM。
- 算法可替换，参数可配，结果可解释。

### 10.6 参考 EasyLRC

- EasyLRC 的音频识别不依赖后端，纯前端 Web Audio API 实现。
- 核心是波形峰值分析，生成校正时间码。
- 隐私政策确认：离线模式下所有处理在浏览器内进行，不上传服务器。
- 启示：频率微调和人声边界识别可设计为纯客户端计算，无需后端。

## 十一、移动端设计（已讨论部分，暂挂起）

- 用户原话：
  > “首先设计手机端打轴。就是在横屏状态下的左侧或者右侧设置一个大按键至于具体的左侧，右侧由创作者自己在设置里头调。然后点击时会有震动反馈。这样子设计最好”
- 已敲定：
  - 横屏打轴，屏幕左侧或右侧放一个大按键。
  - 位置由创作者在设置里选左/右。
  - 点击有震动反馈。
  - 大按键默认打行级，旁边小按钮切字级。
  - 打完一行自动跳到下一行。
  - 播放控制放在另一侧。
  - 波形和歌词块在上方。
  - 打轴模式和非打轴模式可切换，不丢状态。
- 其他移动端交互（竖屏布局、字级打轴方案、日志底部抽屉等）已初步讨论，但用户表示：
  > “暂时还是不太想先聊手机移动端的这个设计。这个我们下次再聊”
